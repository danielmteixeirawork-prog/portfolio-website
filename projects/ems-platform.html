EMS Platform

A full-stack platform for monitoring and controlling data-centre-style infrastructure across multiple sites — built solo, running in production, and operated by the person who wrote it.

  • Sole developer & operator
  • ASP.NET Core (.NET 10)
  • React 19
  • MariaDB + Dapper
  • Worker Services
  • Modbus / SNMP / BACnet / S7
  • Linux · systemd · Nginx

TL;DR — EMS monitors sensors, power and energy, HVAC, UPS, PDUs, access control, digital I/O and alarms across multiple physical sites. It is a from-scratch C#/.NET rewrite of an earlier Node.js/Express system, migrated feature by feature against live traffic. Three cooperating pieces: an ASP.NET Core API + React 19 SPA, a fleet of 9–11 independent protocol workers, and KioskManager for the on-site display boards.

Overview

EMS (Energy/Environment Management System) is a solo-developed, production-deployed system — I act as both developer and operator, running it directly against live infrastructure. It is organised as three cooperating pieces:

  • EMS — the central web application (ASP.NET Core API + React SPA) that users and admins interact with.
  • Services — 9–11 independent background workers that poll field hardware (Modbus, SNMP, BACnet, Siemens S7, GPIO, ping, cameras) and feed the shared database, plus notification and reporting workers.
  • KioskManager — a separate cross-platform desktop tool for fleet-managing the physical kiosk display boards that show EMS dashboards on-site. It has its own write-up.

Architecture

A classic API + SPA split, deployed together behind Nginx on a single host, with MariaDB as the system of record: 

Browser (React SPA)
      │  HTTPS
      ▼
   Nginx  ──────────────▶  ems-backend.service (ASP.NET Core, Kestrel)
      │                          │
      │                          ├─ Dapper (micro-ORM) ──▶ MariaDB
      │                          ├─ Server-Sent Events (live sensor/alarm push)
      │                          └─ MariaDB-backed auth ticket store (custom cookie auth)
      ▼
 static assets (built SPA, served from the API's "public" wwwroot)
  • Backend: ASP.NET Core on .NET 10, MVC-style Controllers → Repositories. No EF Core — raw SQL via Dapper and MySqlConnector (a MySQL-wire-protocol .NET driver that is also MariaDB-compatible), for full control over query shape and performance on a hand-tuned schema.
  • Database engine: MariaDB 10.11, running as mariadb.service.
  • Frontend: React 19 + TypeScript built with Vite, served as static files by the same backend process — one deployable unit, one systemd service, one Nginx vhost.
  • Real-time updates: Server-Sent Events push live sensor readings and alarm state to connected dashboards, with no polling.
  • Auth: cookie-based session auth with a custom MariaDB-backed ticket store (not the default in-memory / data protection flow), CSRF middleware, and a permission-based authorization handler gating admin actions by role and permission.
  • Security middleware: dedicated security-headers, CORS-policy, CSRF, request-ID and audit-log middleware sit in the ASP.NET Core pipeline — every admin mutation is written to an audit_log table.
  • Deployment: a self-contained dotnet publish build installed in place as a systemd unit; Nginx terminates TLS and reverse-proxies to Kestrel.

Two decisions worth calling out

  • The codebase pins a transitive Microsoft.OpenApi version specifically to dodge a known CVE — a stack-overflow DoS in circular-reference OpenAPI parsing — rather than waiting on upstream to bump it.
  • A privileged operations helper (ems-system-helper) brokers root-level actions — service restarts, network configuration — from an unprivileged web process via sudo, instead of running the whole API as root.

Database

MariaDB, schema-managed through versioned SQL migration files (Setup_DB/migrations/) applied by a tracked shell script, with a separate seed/ directory for reference data (sensor-type icon catalogues, for example) and a utilities/ folder for one-off maintenance scripts.

The admin UI itself exposes database backup, performance tuning, partition management and maintenance controllers — database operations are a first-class admin feature here, not just an ops-side concern.

Services — the peripheral worker fleet

9–11independent worker processes
6+field protocols spoken
2CPU targets (x64 + ARM64)

Nine to eleven independent .NET Worker Service processes (Microsoft.Extensions.Hosting), each a long-running daemon polling one class of field hardware and writing readings into the shared MariaDB database the API reads from. Each is its own systemd unit, independently deployable and restartable — a genuine microservice decomposition rather than a monolith, chosen so that a crash or hang in one protocol driver (a flaky Modbus RTU serial line, say) can't take down sensor polling for everything else.

  • Shared conventions across all of them: Serilog file + console logging, MySqlConnector for direct MariaDB access, DotNetEnv for .env-based configuration (credentials, poll intervals, device lists), a common Shared/ project, and a Directory.Build.props for consistent build settings.
  • Most target .NET 8, with the newer additions on .NET 10 — reflecting an incremental migration as the runtime matured.
  • Production binaries are published self-contained and single-file for linux-x64, with a parallel linux-arm64 publish path: the same services run on a standard x64 host and on embedded ARM hardware (Raspberry Pi CM5).

What this project demonstrates

  • End-to-end full-stack ownership: relational schema design and migrations, a typed API layer, a modern React SPA, and a native cross-platform desktop client — all built and operated solo.
  • Protocol-level industrial integration: Modbus (TCP and RTU), SNMP (client and agent), BACnet/IP, Siemens S7, GPIO, and RTSP/ONVIF-style camera control — real fieldbus and OT protocols, not REST-to-REST plumbing.
  • Production operations discipline: audit logging, CSRF and security headers, encrypted credential storage, a privileged-helper pattern instead of running as root, scoped per-service redeploys, and a deploy runbook driven by real incidents — including an rm -rf bug in the publish script that silently wiped production logs, found and fixed from first principles.
  • Deliberate microservice boundaries: each hardware protocol is an isolated, independently restartable systemd service rather than threads inside a monolith — a fault-isolation decision, not a tutorial pattern.
  • Migration discipline: an active, feature-by-feature rewrite of a legacy Node.js system into typed C#, run in parallel with a live production system.
