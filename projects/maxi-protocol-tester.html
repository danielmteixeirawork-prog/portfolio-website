Maxi Protocol Tester

A bench and field tool for data-centre commissioning: test every protocol the monitoring platform depends on — field buses, PLCs, SNMP agents, email and SMS gateways — from one fast, readable desktop app.

  • Design & sole developer
  • C# / .NET 10
  • WPF · MVVM
  • Modbus TCP / RTU
  • Siemens S7
  • SNMP v3
  • MailKit
  • xUnit v3

TL;DR — Before a monitoring system goes live, every meter, UPS, PLC and notification channel must be proven to answer correctly. The tool technicians used was a 2018 WinForms application — one 4,000-line form, a native 32-bit PLC library, vendor DLLs and several latent bugs. I rewrote it from the ground up in .NET 10, using the decompiled original as the functional specification: a layered, dependency-injected WPF/MVVM app covering Modbus TCP and RS485 RTU/ASCII, Siemens S7, SNMP v1/v2c/v3, SMTP and email-to-SMS, and a Yeastar NeoGate GSM gateway. It decodes registers in every numeric type and word order, turns failures into probable causes, never freezes the window, and is covered by 52 automated tests — several of them running real protocol stacks against in-process slaves and servers, with no hardware attached. It ships as a single self-contained executable for site laptops.

Overview

Commissioning a data-centre monitoring installation means working through dozens of devices, each speaking a different protocol, and answering the same questions every time: is it reachable, is the address right, does the value decode correctly, will the alarm actually reach a phone? The tester puts all of that in one app, one page per protocol:

PageWhat the technician does
ModbusRead and write registers and coils over TCP or a USB↔RS485 converter; decode values; poll continuously
Siemens S7Read data-block bytes and force bits or bytes on S7-1200/1500/300/400 PLCs
SNMPGET and WALK on UPS, PDU and environmental agents, including fully secured SNMPv3
Email & SMS via emailProve the SMTP server or internal relay — and email-to-SMS gateways — will deliver alarms
NeoGate TG100Check the SIM and network registration, then send test SMS to several recipients

Architecture

MPT.slnx
├── Mpt.Core          pure logic — no I/O, no UI
│     register decoding · word orders · device presets · AMI protocol · traffic log contract
├── Mpt.Protocols     one client per protocol, all async, all logging TX/RX
│     Modbus (TCP + serial) · S7 · SNMP · SMTP · NeoGate AMI
├── Mpt.App           WPF shell
│     Generic Host DI · one ViewModel + View per protocol · themes · settings · traffic log
└── tests
      Mpt.Core.Tests        decoders, legacy-button equivalence, AMI parsing
      Mpt.Protocols.Tests   Modbus TCP/RTU/ASCII, NeoGate, SNMPv3 security selection
  • Clean layering — protocol logic and decoders know nothing about WPF, so they are unit-testable and reusable.
  • Microsoft.Extensions.Hosting composes the app; each protocol page is registered as a PageViewModel, and registration order is the navigation rail.
  • MVVM with source generators — CommunityToolkit.Mvvm [ObservableProperty] / [RelayCommand]; a single base RunAsync gives every operation the same busy state, timing, status line and error handling.
  • Modern build hygiene — central package management, pinned SDK via global.json, .slnx solution, code style enforced at build time, nullable reference types throughout.

Modbus — from raw registers to real values

  • TCP and serial behind one API — ModbusTcpEndpoint and ModbusSerialEndpoint share the same read/write calls (FC01–06, FC16); serial supports RTU and ASCII framing with configurable baud, parity, data and stop bits.
  • Probe-style connections — each call opens and closes its own socket or COM port, so a dropped link or an unplugged USB converter never leaves a stale session.
  • Real cancellation — NModbus has none, so cancelling closes the underlying socket or port to unblock it; blocking serial I/O runs off the UI thread.
  • Converters identified by name — COM ports are listed with their Device Manager names via WMI (e.g. COM5 · USB-SERIAL CH340), so the right converter is obvious among several.
  • No more 0- vs 1-based guessing — a live hint shows exactly which addresses go on the wire.
  • Decode inspector for the selected register: a matrix of Int32 / UInt32 / Float32 / Int64 / UInt64 / Float64 × ABCD / CDAB / BADC / DCBA, a 16-bit view, and device presets that walk a whole block (Janitza float, Schneider PM500, base-10000 energy counters…), named after the old tool's buttons so technicians recognise them.
  • Continuous polling at a configurable interval, stopping cleanly on the first failure.

Siemens S7, SNMP, email and GSM

  • S7 — addresses in TIA Portal notation (DB1.DBX0.3), a per-byte bit grid with the target bit highlighted, bit and byte writes (decimal, hex or binary input), CPU presets that set the right default slot, and an ISO-TCP port 102 probe with latency.
  • SNMP — GET on several OIDs and WALK (bulk walk on v3), quick picks for standard OIDs, and full SNMPv3 USM: engine discovery, all three security levels, MD5 through SHA-512, DES/AES-128/192/256, with password lengths validated before anything is sent.
  • Email — STARTTLS, SSL/TLS or plain relay with the port following the security mode, plus email-to-SMS gateway testing (one message per number, number in the subject).
  • NeoGate TG100 GSM gateway — a purpose-built AMI client: validates the banner, logs in, parses gsm show spans into a SIM state (active, no SIM, no network…), refuses to send if the SIM isn't ready, sends each SMS in its own session so one failure never blocks the rest, and confirms delivery by correlating a per-message ID with Status: 1.

Errors that explain themselves

Most commissioning time is lost working out why something doesn't answer. Every protocol client translates low-level failures into the most likely cause:

On the wireWhat the technician reads
Modbus exception 02Illegal address — check whether the device counts from 0 or 1
Modbus exception 0BThe device behind the gateway didn't answer — check the Unit ID
Serial CRC failureUsually baud or parity mismatch, swapped A/B wires, or missing RS485 termination
COM port access deniedThe port is in use by another program
S7 connection errorCheck rack/slot and that PUT/GET access is enabled in TIA Portal
S7 read rejectedThe DB must exist, be non-optimised and be large enough
SNMPv3 report: wrong digestsAuthentication rejected — check MD5/SHA and the password
SNMPv3 decryption failureCheck the privacy protocol (DES/AES) and password
AMI login responseLogin refused — check the API user and secret on the gateway

Built for the field

  • Traffic log — a dockable panel (Ctrl+L) with every TX, RX, OK, WARN and ERR line, timestamped per channel, mirrored to a daily log file, copyable and exportable, and capped so long sessions stay responsive.
  • Never freezes, never quits — all I/O is async; unhandled UI exceptions are logged and the app keeps running, so a bug never ends a commissioning session. Startup failures are written to a diagnostics file.
  • Guards on real-world actions — sending real emails and SMS requires explicit confirmation, and recipient lists are validated as you type, with suspicious numbers flagged.
  • Remembers the site — last IP, port and settings per page, saved to JSON with an atomic write (temp file, then move) and a corrupt file falling back to defaults. SMTP passwords, SNMPv3 keys and gateway secrets are encrypted with DPAPI for the current Windows user.
  • Fits the hardware — the window sizes itself to the screen, from a small site laptop to an office monitor.

Rewriting a legacy tool

The decompiled 2018 application served as the functional specification, and every legacy feature has a documented home in the new app. Rebuilding it properly surfaced latent bugs that were fixed along the way:

  • S7 — the CPU model chosen in a combo box was silently used as the number of bytes to read, and rack/slot were hard-coded to 0/0, which breaks S7-1200/1500 (normally slot 1).
  • GSM gateway — an internal copy of the client re-sent the login command where it should have sent the SMS command.
  • IEEE 754 decoding — the old button combined words in a byte order no real device uses; the new decoder shows all four standard orders side by side.
  • UX — generic exception message boxes and blocking calls replaced by explained errors and a responsive UI.

Testing without hardware

  • Modbus TCP against a real NModbus slave listening on loopback.
  • Modbus RTU and ASCII against a real NModbus slave joined by an in-memory full-duplex serial line with serial-port timeout semantics — the complete framing and CRC path, with no RS485 converter.
  • NeoGate against a scripted AMI server that behaves like the real gateway (right and wrong secrets, SIM present and missing, SMS acknowledgement by message ID).
  • Legacy equivalence tests prove the new decoders give the same results as the old device buttons, byte for byte.
  • SNMPv3 security selection tested for every level, hash and cipher.
  • The publish script runs the full suite first and refuses to build the executable if anything fails.

What this project demonstrates

  • Deep protocol knowledge — Modbus framing, addressing and word order; S7 data-block addressing; the SNMPv3 security model; AMI as a text protocol.
  • Legacy modernisation — reading a decompiled binary as a specification, preserving behaviour where it was right and fixing it where it wasn't.
  • Software design — clean separation of pure logic, protocol clients and UI; dependency injection; MVVM; consistent operation handling.
  • Testing hard-to-test code — real protocol stacks exercised end to end without devices, cables or gateways.
  • Tooling for the people who use it — diagnostics written for technicians, safe defaults, encrypted secrets, single-file deployment.
