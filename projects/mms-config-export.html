MMS Configuration Export

A one-click tool that reads an MMS installation's database and produces the documentation technicians and customers actually need — sites, equipment, sensor protocol settings, inventory and alarm rules — as formatted Excel workbooks.

  • Design & sole developer
  • Python 3
  • openpyxl
  • mysql-connector-python
  • MySQL / MariaDB
  • PyInstaller

TL;DR — An MMS installation's configuration is spread across dozens of related tables, with protocol settings stored as generic key-value rows per sensor. This tool connects to the MySQL or MariaDB database and produces three formatted workbooks and an image folder: a per-site configuration workbook that pivots each sensor's protocol parameters into columns, an equipment inventory with MAC addresses resolved from the local ARP table, and an alarm trigger matrix that describes rules exactly as the alarm engine evaluates them. It adapts to the schema it finds, logs every step, and ships as a single PyInstaller executable — nothing to install on the technician's PC.

Overview

Commissioning, audits, handovers and migrations all need the same thing: an accurate, readable picture of how an installation is configured. Getting it from the MMS UI means clicking through every site and sensor; getting it from the database means knowing the schema. This tool does it in one run, straight from the source of truth: 

MMS_Export.exe  (+ optional config.json)
   │
   ├─▶ {Client}_mms.xlsx          client config · users · one sheet per site
   ├─▶ Equipments_{Client}.xlsx   flat equipment inventory (+ MAC from ARP)
   ├─▶ Triggers_{Client}.xlsx     alarm rules per equipment and sensor
   └─▶ {Client}_mms_images/       site images per site  +  SiteGroups/

Tech stack

Language Python 3
Database MySQL or MariaDB via mysql-connector-python (pure-Python mode)
Excel openpyxl — styled tables, frozen panes, internal hyperlinks, wrapped multi-line cells
Packaging PyInstaller single-file console executable with a custom .spec

The workbooks

1. Configuration workbook — {Client}_mms.xlsx

  • Client Config sheet — SMTP email and GSM/SMS gateway settings with human-readable labels (internal timer keys excluded), followed by the user list with Yes/No flags.
  • One sheet per site — site details (site group and parent resolved to names, not IDs), then for each equipment a details table and a sensor configuration table.
  • Navigation — a "Jump to equipment" row of internal hyperlinks at the top of each site sheet, for sites with many devices.

2. Equipment inventory — Equipments_{Client}.xlsx

  • One row per device: name, IP, model, serial number, firmware and MAC address.
  • Empty username and password columns for technicians to complete on site — the file doubles as a commissioning checklist.

3. Alarm trigger matrix — Triggers_{Client}.xlsx

  • One section per equipment (with site and type), one row per sensor, and every trigger listed on its own line in the same cell — e.g. Value range: -∞ to 10 (Warning), Bit 3 = 1 (Critical).
  • Faithful to the alarm engine — an open (NULL) lower or upper bound is shown as -∞ / ∞, because that is how the engine evaluates it; a blank would suggest a limit that doesn't exist.
  • Common Portuguese severity names are translated to English, sensors without rules are flagged as "No trigger configured", camera equipment is excluded, and row heights grow with the number of rules.

Pivoting key-value data into columns

MMS stores protocol settings generically: each reading type (SNMP, Modbus, Siemens S7, Hikvision, access control…) defines its own parameter types, and each sensor stores values against them. The export turns that into readable columns:

  • Fixed columns for every sensor — name, sensor type, port, IP, reading type and UI/graph display settings.
  • Dynamic columns — one per parameter used by that equipment's reading types, in the platform's defined order: SNMP OID, format, conversion; Modbus register, function code; Siemens S7 DB number, formula; Hikvision channel, RTSP and playback paths; access control readers, door number.
  • Values matched by reading type as well as name, so identically named parameters from different protocols never bleed into each other.
  • Readable headers — internal parameter names map to friendly labels; unknown names pass through unchanged, so new protocols still export correctly.
  • Batched queries — parameter types and values are loaded once per equipment with parameterised IN (…) queries, not per sensor.

MAC resolution without network scanning

  • The local ARP table (arp -a on Windows, arp -n elsewhere) is parsed once and cached, then each equipment IP is looked up in it.
  • No pings, no ARP requests — the export generates no traffic on the customer network and stays fast; MACs appear for devices the PC has recently talked to.
  • It can be switched off entirely with resolve_mac in the config.

Robust across installations

  • Schema-tolerant — each section checks that its tables exist and degrades with a clear note in the workbook, so older or partial databases still export.
  • Schema knowledge in one place — all table and column names are constants at the top of the script, so adapting to a schema variant is a contained change.
  • Soft-delete aware — deleted sites, equipment and sensors are excluded consistently, including NULL delete flags.
  • Handles MySQL BIT columns, which arrive as bytes, and renders them correctly as Yes/No.
  • File-system safe — client, site and folder names are sanitised for Windows, and sheet names respect Excel's 31-character and character rules.
  • Collects images — site and site-group images are copied from the web application's image folders (configurable paths) into one folder per site, ready for handover.

Packaging & diagnostics

  • Single executable — PyInstaller with a custom .spec. mysql-connector loads its authentication plugins and locale modules by name at runtime, which static analysis misses, so they are collected explicitly as hidden imports.
  • Sidesteps a known Windows failure — the connector runs in pure-Python mode (use_pure=True) to avoid error 2059, where the C extension cannot load the mysql_native_password plugin DLL.
  • Portable configuration — an optional config.json next to the executable overrides connection, image paths and MAC resolution.
  • Field-debuggable — step-by-step progress to the console and to a timestamped mms_export_log.txt; on failure the full traceback is logged and the window waits for Enter instead of vanishing.
  • Distribution — a build script produces the executable and copies it into a publish\ folder with English and Portuguese instructions.

What this project demonstrates

  • Data-modelling fluency — navigating a large relational schema and pivoting key-value storage into a readable, per-protocol layout.
  • Semantic accuracy — documenting alarm rules as the engine evaluates them, not just as the columns store them.
  • Documentation as a product — output formatted for the technicians and customers who will actually use it.
  • Shipping Python to non-developers — single-file packaging, runtime dependency pitfalls handled, and diagnostics that work without a developer present.
