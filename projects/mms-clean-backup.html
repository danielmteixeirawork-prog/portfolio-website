MMS Clean Backup

A field tool that takes a portable, configuration-complete copy of an MMS installation's database — without its history — so a system can be cloned, moved or reproduced in minutes.

  • Design & sole developer
  • PowerShell
  • MySQL / MariaDB
  • mysqldump
  • PS2EXE
  • Windows

TL;DR — A full dump of a production MMS database is dominated by years of sensor readings, alarm history and access logs — slow to move and irrelevant for most support work. This tool produces a cleaned backup: every table, routine, trigger and event, plus all configuration data, with seven operational tables exported structure-only. The live database is never modified: the copy is taken in a consistent single transaction, dumped in two ordered passes so it always re-imports cleanly, and can be restored under any database name side by side with the original. Works with MySQL and MariaDB, and ships as a single 37 KB executable with a config file and bilingual instructions.

Overview

The tool exposes three operations from a simple console menu:

  • (1) Create backup — cleaned .sql dump; the live database is unchanged.
  • (2) Create database and import a dump — restore any dump into a new database.
  • (3) Backup, then restore — clone an installation into a new database in one go (e.g. a test copy on the same server).

Typical uses: preparing a staging or test environment, moving an installation to a new server, reproducing a customer issue on a bench machine, and taking a lightweight configuration backup before a risky change.

What "clean" means

FULL DATA  (configuration)                STRUCTURE ONLY  (operational history)
────────────────────────────────          ──────────────────────────────────────
sites, equipment, sensors,                sensor_readings        alarm
parameters, alarm rules, users,           alarm_ignore           action_log
notification settings, client, …          notification_to_process
+ routines · triggers · events            notification_error     access_log

Everything needed to bring an installation back up is kept; only the tables that grow without bound are emptied — and they still exist in the backup, so the restored database is structurally complete and fully functional.

How the backup works

MMSBackup.exe
  ├─ read config.json (or defaults) → prompt for password if not configured
  ├─ SELECT name FROM client  →  {client}_mmsCleanBackup_{yyyyMMdd_HHmmss}.sql
  │
  ├─ pass 1: mysqldump --single-transaction --no-data  <7 operational tables>
  │            └─ raw stdout stream ──▶ backup.sql  (create)
  │
  └─ pass 2: mysqldump --single-transaction --routines --triggers --events
               --ignore-table=<each of the 7>  <database>
               └─ raw stdout stream ──▶ backup.sql  (append)
  • Ordering is deliberate — the empty table structures are written first, so the triggers and foreign keys in the rest of the dump can reference them at import time.
  • Consistent without locking — --single-transaction takes an InnoDB snapshot, so the backup runs against a live system without blocking the services writing to it.
  • Binary-safe output — mysqldump's stdout is copied byte for byte from the process's base stream straight into the file, bypassing PowerShell's text pipeline and redirection, which would re-encode the dump and can corrupt UTF-8 data.
  • Fails loudly — each pass checks the exit code, captures stderr, and rejects an empty output file.
  • Meaningful file names — the customer name is read from the client table, sanitised, and combined with a timestamp.

How the restore works

  • Creates the target database with utf8mb4 / utf8mb4_unicode_ci.
  • Restores under any name — the dump's USE statements are rewritten to the new database, so a copy like mms_test can live next to the original without touching it.
  • Imports through the mysql client, then verifies the result by counting tables in information_schema.
  • Handles trigger side effects — because triggers can fire during import and insert rows into the cleaned tables, the tool offers to truncate those seven tables again, with foreign-key checks temporarily disabled.

Built for technicians

  • Single executable — the script is compiled with PS2EXE into MMSBackup.exe. A build script installs the module if needed, builds, and copies the result into a publish\ folder ready to hand out.
  • Configurable per site — config.json sets the client-tools path, backup folder, host, port, user, password and default database, so it works with any MySQL or MariaDB installation, local or remote. Only non-default host and port are passed on.
  • No stored secrets by default — when no password is configured, it is requested at runtime through a secure prompt.
  • Friendly failure handling — a global trap shows the error and keeps the window open, ignores mysql's benign "password on the command line" warning, and falls back to a sensible working folder when running as an executable (where $PSScriptRoot is empty).
  • Bilingual instructions — English and Portuguese usage guides ship in the publish folder.

What this project demonstrates

  • Understanding the data, not just dumping it — knowing which tables carry configuration versus history, and how triggers and foreign keys constrain restore order.
  • Safety first — read-only, consistent snapshots of a live production database, and restores that never overwrite the source.
  • Careful process handling — raw byte streaming, exit-code checks and stderr capture around external CLI tools.
  • Operational empathy — a menu-driven, single-file tool that non-developers can run safely in the field.

My role

Sole developer: backup strategy and table selection, the dump and restore logic, packaging and build pipeline, and the end-user documentation.
