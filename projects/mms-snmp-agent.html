MMS SNMP Agent

A small, always-on integration service that turns the MMS platform's sensor database into a standard SNMP agent — so any network management system can poll live readings without touching the database or the MMS UI.

  • Design & sole developer
  • C# / .NET 8
  • Worker Service
  • Windows Service
  • SNMP v1 / v2c
  • MySQL / MariaDB
  • ClosedXML
  • PowerShell

TL;DR — Built for a customer who wanted MMS sensor data inside their own NMS, and designed to be reused on any MMS deployment. A .NET 8 Worker Service, running as a Windows service, loads every active sensor into an immutable, sorted OID snapshot every 15 s and answers GET, GETNEXT and GETBULK requests from it over UDP — the SNMP handling is written directly on the socket. It works against both MySQL and MariaDB, is hardened for 24/7 unattended operation (self-restarting loops, exponential backoff, circuit pause), and ships a one-click tool that generates the Excel OID map used to configure the monitoring side.

Overview

MMS keeps the latest value for every sensor across the monitored equipment. The service was first commissioned by a customer whose operations team already ran a network management system and wanted those values there, not in another dashboard. SNMP is the one protocol every NMS speaks, so the agent was built generically: nothing in it is specific to that customer, and it can be dropped onto any MMS installation. The goals were:

  • Standard protocol, zero client-side work — any SNMP v1/v2c manager can walk and poll the data.
  • No load or risk on the platform — the agent only reads the database, on a fixed interval, no matter how often it is polled.
  • Works with MySQL and MariaDB — it runs unchanged against either engine, through MySqlConnector and portable SQL.
  • Self-documenting — every deployment can generate an up-to-date spreadsheet mapping each OID to its equipment, sensor, unit, value meanings and alarm rules.

Architecture

 NMS ──SNMP v1/v2c (UDP 1161)──▶  MmsSnmpAgent  (Windows service "MMSSnmpAgent")
                                  │
                                  ├─ SnmpAgentHostedService
                                  │    UDP listener → parse → community check
                                  │    → GET / GETNEXT / GETBULK → response
                                  │              │ reads
                                  │              ▼
                                  ├─ SensorSnapshotCache   (one reference to an
                                  │    immutable SensorMibSnapshot, atomic swap)
                                  │              ▲ publishes
                                  │              │
                                  └─ SensorSnapshotRefreshService
                                       every 15 s: one SQL query → build snapshot
                                       on failure: exponential backoff + circuit pause
                                                     │
                                                     ▼
                                          MMS database  (MySQL or MariaDB)
  • Two hosted services and one shared cache, composed with Microsoft.Extensions.Hosting and registered as a Windows service through AddWindowsService.
  • Reads and writes are fully decoupled. The refresh service builds a complete new snapshot off to the side and publishes it with a single reference swap; the listener grabs the current snapshot once per request. A response never mixes two refreshes, and there are no locks on either side.
  • Polling cost is independent of NMS traffic — however aggressively the network is polled, the database sees one query per refresh interval.
  • Configuration is bound through IOptionsMonitor in separate Database and SnmpAgent sections: bind address, port, community, enterprise number, value scale factor, refresh interval and verbose logging.

The OID model

Every active sensor becomes a row in a private enterprise table:

1.3.6.1.4.1.<PEN>.1.<sensorId>.<column>

  column 1   value_scaled        Integer32     latest reading × scale factor
  column 2   last_reading_time   OctetString   ISO-8601 UTC timestamp
  • Integer-only values. SNMP has no decimal type, so readings are multiplied by a configurable scale factor — 1 sends the rounded engineering value, 10000 keeps four decimal places for the NMS to divide back. Values are rounded away from zero and clamped to the Integer32 range.
  • Explicit sentinels. When the parent equipment is offline the value is -1, so the NMS can alarm on "equipment offline" separately from any threshold on the reading itself.
  • Freshness is visible. The timestamp column lets the NMS tell stale data from live data — including while the database is unreachable.
  • Only live objects are exposed. Inactive or deleted sensors, and sensors on deleted equipment, are filtered out, so the OID table matches exactly what MMS itself shows.

SNMP engine

Rather than a full agent framework, request handling is written directly on a UdpClient, with SharpSnmpLib used only to parse and encode messages:

  • GET — direct lookup in a FrozenDictionary keyed by OID; unknown OIDs return noSuchObject.
  • GETNEXT — a binary search over the pre-sorted OID list, O(log n) per lookup regardless of table size, returning endOfMibView past the last object. This is what makes snmpwalk work.
  • GETBULK — implemented to RFC 3416: the first non-repeaters variables resolve as single GETNEXTs, the rest repeat up to max-repetitions. NMS tools rely on this to walk large tables in few round-trips.
  • Defensive by default — v1/v2c only; wrong-community requests and trap/inform PDUs are dropped; malformed datagrams are logged at debug level and skipped; a failure on one message never stops the listener.
  • Listens on UDP 1161 by default to avoid needing elevated privileges for port 161, with a configurable bind address per network interface.

Built to run unattended

The service runs on customer infrastructure where nobody is watching it, so availability and self-recovery drove the design:

  • One fault doesn't kill the process — BackgroundServiceExceptionBehavior.Ignore stops a crashed hosted service from taking down the host.
  • Self-restarting loops — each service wraps its main loop in a supervisor that logs at Critical and restarts after a short delay (5 s for the listener, 10 s for the refresh loop), while still shutting down cleanly on cancellation.
  • Database failures degrade gracefully — failed refreshes back off exponentially from 5 s up to 5 min, and after 5 consecutive failures a circuit pause of at least 2 min stops the agent from hammering a struggling database. The backoff arithmetic is overflow-safe.
  • Keeps serving through an outage — the last good snapshot stays live, so the NMS keeps getting answers while the timestamps show how old they are.
  • Operational logging — a summary on every refresh (sensor and OID counts), plus a verbose mode with sensor-ID range, offline-sensor count and first/last OID for field diagnostics.

OID documentation export

An SNMP integration is only as good as its handover document, so the documentation is generated straight from the live database and can never drift from what the agent actually exposes: 

ExportMmsSnmpOidTable.bat
   └─▶ PowerShell: resolve config → find a real mysql client → run SQL template
          └─▶ mysql --batch  (TSV)
                 └─▶ MmsOidTableToXlsx.exe  (ClosedXML)  ──▶  mms_snmp_oid_table.xlsx
  • The workbook — a first sheet with the SNMP connection details (IP, port, version, community), then one sheet per equipment listing each sensor's name, unit, value map (e.g. 0=Closed, 1=Open), its alarm rules in readable form (>= 30 — High temperature [sev 2], bit3=1 — …) and the exact OID.
  • SQL does the heavy lifting — GROUP_CONCAT and CASE expressions render threshold, range and bit-mask alarm triggers as readable rules, with a separator token so multi-line cells survive the TSV hand-off.
  • A polished spreadsheet — styled headers, zebra striping, frozen header rows, wrapped multi-line columns sized to their longest line, and sheet names sanitised to Excel's 31-character uniqueness rules.
  • Robust on real field PCs — config from appsettings.json or a separate credentials file with environment-variable overrides; locates a genuine mysql.exe from either a MySQL or a MariaDB installation while skipping the WindowsApps execution-alias shims that break on many Windows machines; passwords masked in debug output.
  • Packaged with the agent — a custom MSBuild target (AfterTargets="Publish") builds the xlsx tool into tools\, so every published package can produce its own documentation.

Deployment

  • Build — framework-dependent dotnet publish for win-x64, with the scripts copied into the package through MSBuild content rules.
  • Install — MmsSnmpAgent-RunOrInstall.bat works from both the source tree (dev run, publish, publish + install) and a pre-built package (console test run, install). It checks for administrator rights, cleanly stops and removes an existing service before reinstalling, registers MMSSnmpAgent with automatic start, and tells the operator where to configure it.
  • Double-click friendly — an interactive menu and pause-on-error mean a field technician can deploy it without knowing .NET.

What this project demonstrates

  • Protocol-level work — implementing SNMP agent semantics (GETNEXT ordering, GETBULK per RFC 3416, v2c exception values) instead of configuring an off-the-shelf agent.
  • Lock-free concurrency — immutable snapshots with a single atomic reference swap keep the hot request path contention-free and always consistent.
  • Reliability engineering for unattended systems — supervised loops, exponential backoff, a circuit pause, and graceful degradation that keeps serving data through a database outage.
  • Designing for reuse — built for one customer but kept generic: configuration-driven, and portable across MySQL and MariaDB.
  • Designing for the consumer — integer scaling, offline sentinels and timestamps chosen so the NMS can alarm on the data correctly.
  • Handover as part of the product — generated, always-accurate OID documentation and one-click installation for field deployment.
