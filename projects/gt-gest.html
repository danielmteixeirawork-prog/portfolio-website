Gt Gest

An internal management platform: the web application the team uses to run warehouse stock, day-to-day tasks, and the technical record of every customer.

  • Design & full-stack development
  • React 19
  • TypeScript
  • ASP.NET Core (.NET 10)
  • Dapper
  • MariaDB
  • IIS

TL;DR — Internal full-stack platform in React 19 + TypeScript and ASP.NET Core .NET 10, with Dapper over MariaDB. It combines stock management built on an immutable movement ledger with concurrency-safe reservations, a drag-and-drop Kanban board with calendar and Excel export, and a customer record with encrypted, audited credentials. A single process serves both the API and the SPA on IIS.

Overview

Gt Gest replaces spreadsheets with one internal application. It has three modules:

  • Stock — items, categories, receipts, issues and adjustments, per-project reservations, and a warehouse dashboard.
  • Work (tasks) — a drag-and-drop Kanban board plus table and calendar views, subtasks, comments, labels, task links, followers, change history, saved views, a personal "My work" page, a team dashboard, and Excel export.
  • Customers — contacts, platforms, interventions, equipment, documents, backups and remote access, with a per-customer event log.

Architecture

Browser ──HTTPS──▶ IIS ─ one ASP.NET Core process
                          │
                          ├─ /api/*  ─▶ Controllers  (validate · delegate · ApiResponse envelope)
                          │                 ├─▶ Services      (writes + business rules)
                          │                 └─▶ Repositories  (reads only)
                          │                            │ Dapper / hand-written SQL
                          │                            ▼
                          │                       MariaDB 10.6 (InnoDB)
                          │
                          └─ /*      ─▶ wwwroot (built React SPA) ─▶ index.html
  • One process, one origin: ASP.NET Core serves the API under /api and the compiled SPA from wwwroot. No CORS, no second web server. Unknown /api routes return JSON 404s; everything else falls through to index.html for React Router.
  • Strict separation of responsibilities: repositories only read, services only write (and own the business rules), controllers only validate, delegate, and wrap the result in a common ApiResponse envelope. When a number looks wrong, there is exactly one place to look.
  • Exception middleware that translates domain errors into HTTP status codes with Portuguese messages.
  • Tuned HTTP caching: hashed assets are served immutable while index.html goes out no-cache, so deployments reach browsers immediately.

Authentication & security

  • Passwords hashed with BCrypt (work factor 12).
  • Cookie auth with server-side sessions via a custom ITicketStore: the cookie carries only the session id, the ticket lives in a database table, and an administrator can revoke a session instantly. HttpOnly, SameSite=Strict, sliding expiration.
  • Two layers of CSRF defence: on top of SameSite, a double-submit token signed with HMAC-SHA256 and compared in constant time — so nobody can plant a valid cookie/header pair.
  • Login rate limiting per IP rather than per user, to stop password spraying, with ForwardedHeaders restricted to loopback so the client IP cannot be spoofed.
  • admin/user roles enforced with [Authorize(Roles)].
  • Customer credentials encrypted with ASP.NET Data Protection under a dedicated purpose: they never appear in list responses, and every read is logged with the name of whoever requested it.
  • Customer files stored outside wwwroot: streamed to disk while the SHA-256 hash is computed, then stored under that hash as the filename — the browser-supplied name never touches the file system — with a size limit and access only through authenticated endpoints.
  • HSTS, a persisted key ring (sessions survive IIS recycles), and a one-time initial administrator bootstrap.

Technical highlights

  • Stock as an accounting ledger: the on-hand quantity is only a cache of the sum of movements. Every change writes its movement in the same transaction, movements are append-only (corrections are adjustments), and a reconcile endpoint recomputes quantities and reports drift.
  • Reservations vs. stock: available = on hand − active reservations. A reservation moves no stock; only fulfilling it generates the associated issue. Admin-forced over-commitment shows up as negative availability instead of being hidden.
  • Concurrency: every operation on an item starts by locking the row (SELECT … FOR UPDATE), so two people reserving the last unit queue up instead of both succeeding. There are dedicated tests for this.
  • Integrity enforced in the database: CHECK constraints that forbid negative balances, DECIMAL(14,3) quantities, and timestamps always in UTC.
  • Kanban ordering by fractional index, so cards move without renumbering the whole column.
  • Saved views and URL-encoded state: filters live in the URL, so they can be shared or saved.
